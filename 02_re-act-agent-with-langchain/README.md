# ДЗ №2 — ReAct-агент у LangGraph

Тревел-планер **«Куди їхати на вихідні»**: користувач ставить одне питання природною мовою,
агент сам вирішує, які інструменти й у якому порядку викликати, і повертає структуровану відповідь.

## Домен і інструменти

Чотири інструменти, усі на публічних API без ключа:

| Інструмент | Джерело | Що робить |
|---|---|---|
| `geocode` | Open-Meteo Geocoding | назва міста → координати, країна |
| `weather`  | Open-Meteo Forecast | поточна погода + прогноз на 1–7 днів за координатами |
| `currency` | НБУ (statdirectory/exchange) | сума в іноземній валюті → гривні за офіційним курсом |
| `facts`    | Українська Вікіпедія (REST summary) | коротка довідка про місто |

Кожен інструмент має Pydantic v2 схему з `Field(description=...)`, щонайменше один
`field_validator` і docstring, який LLM читає під час tool selection.

## Архітектура

```
travel_agent/
  config.py       # провайдер LLM, модель, ліміти — одне місце для змін
  tools.py        # 4 інструменти: Pydantic-схеми + HTTP-виклики
  graph.py        # StateGraph: agent → tools → agent → respond, захисні механізми
  trajectory.py   # історія повідомлень → плаский JSON-лог
  cases.py        # 5 тест-кейсів + 2 демонстрації захисних механізмів
  main.py         # CLI
tests/            # офлайн-тести (LLM і мережа замокані)
```

Граф:

```
        ┌───────────────────────────────┐
        ▼                               │
[agent] ──router──► [tools] ────────────┘
   │
   └──router──► [respond] ──► END
```

- **agent** — LLM з `bind_tools(TOOLS)`; перед викликом перевіряє `max_steps` і `timeout`,
  після — чи не повторився tool call.
- **tools** — `ToolNode` з langgraph.prebuilt; помилки валідації та мережі повертає агенту
  як `ToolMessage`, а не як виняток, тож агент може виправитися.
- **router** — conditional edge: є tool calls і немає `stop_reason` → `tools`, інакше → `respond`.
- **respond** — `with_structured_output(TravelAnswer)`: `city`, `summary`, `facts[]`, `warnings[]`.

Фінальна відповідь будується не з сирої історії, а з текстового переказу траєкторії. Інакше,
коли захисний механізм зупиняє агента на повідомленні з незакритими tool calls, structured
output падає на невалідній історії.

## LLM-провайдер

`ChatOpenAI` з LangChain, спрямований на **OpenRouter** (`https://openrouter.ai/api/v1`),
модель `xiaomi/mimo-v2.5`. Модель і base URL — константи в `config.py`.

Ключ — `OPEN_ROUTER_API_KEY` у `.env` (gitignored).

## Запуск

```bash
cd 02_re-act-agent-with-langchain
./setup.sh                  # .venv + залежності + шаблон .env
./run.sh                    # прогін усіх тест-кейсів → test_results.json + trajectory.json
./run.sh --query "Яка погода у Кракові?"          # один запит
./run.sh --query "..." --max-steps 2 --timeout 5  # з навмисно затісними лімітами
./tear_down.sh              # прибрати .venv та згенеровані артефакти

source .venv/bin/activate && pytest    # 28 тестів, офлайн, без витрат на API
```

## Захисні механізми

| Механізм | Реалізація | Що відбувається при спрацюванні |
|---|---|---|
| `max_steps` | лічильник `steps` у стані, перевірка на вході у вузол `agent` | `stop_reason`, перехід одразу до `respond` |
| `timeout` | `deadline = start + timeout`, перевірка там само | те саме |
| детекція зациклення | `seen_calls` — підписи `назва(відсортовані аргументи)` | повторний підпис → `stop_reason`, інструмент **не** виконується |

У всіх трьох випадках агент не падає, а йде у `respond` і чесно виписує брак даних у `warnings`.
Додатково стоїть `recursion_limit` самого LangGraph як підстраховка на випадок помилки в лічильниках.

Артефакти: `trajectory.json` (усі кроки всіх прогонів: query / thought / action / observation),
`test_results.json` (query, expected, actual, steps, tool_calls, час, ліміти, траєкторія).

## Аналіз результатів

Прогін від 2026-07-28, модель `xiaomi/mimo-v2.5`, ліміти за замовчуванням `max_steps=6`, `timeout=90s`.

| Кейс | Кроків | Інструментів | Час | Результат |
|---|---|---|---|---|
| `one_tool_currency` — 100 USD у гривнях | 2 | 1 | 11.2 с | ✅ курс НБУ, 4492.77 грн |
| `chain_geocode_weather` — погода у Кракові | 3 | 2 | 19.8 с | ✅ ланцюжок geocode → weather |
| `compare_two_cities` — Львів чи Одеса | 3 | 4 | 42.0 с | ✅ 2×geocode + 2×weather, рекомендація Одеси |
| `all_four_tools` — Чернівці: погода, факти, 50 EUR | 3 | 4 | 58.6 с | ✅ усі чотири інструменти |
| `nonexistent_city` — «Ксйцукенг» | 2 | 1 | 8.2 с | ✅ не вигадав погоду, попросив уточнити назву |
| `guard_max_steps` (ліміт 2) | 2 | 6 | 33.3 с | ⛔ `max_steps`, часткова відповідь + warnings |
| `guard_timeout` (ліміт 5 с) | 1 | 3 | 14.4 с | ⛔ `timeout`, немає погоди, warning про це |

**Де агент працює добре.** Планування ланцюжків він тримає впевнено: жодного разу не викликав
`weather` без попереднього `geocode`, хоча це правило є лише в системному промпті. Паралельні
виклики використовує сам — у порівнянні двох міст обидва `geocode` пішли одним кроком, тому
складний кейс на 4 інструменти вклався у ті самі 3 кроки, що й простий на 2. На неіснуючому
місті не галюцинував: отримав `{"error": ...}` від `geocode` і чесно повернув «не знайдено».

**Де помиляється.**
- Сам обирає `days` для `weather` непослідовно: на запит «погода зараз» одного разу взяв
  `days=1`, іншого — `days=3`. Формально не помилка, але відтворюваність страждає.
- Форматує `summary` у Markdown з таблицями та емодзі, хоча схема просить «коротку відповідь».
  Структурований вихід гарантує поля, не стиль; для суворого формату потрібен окремий валідатор
  довжини або приклад у промпті.
- Питання про «вихідні» трактує як «найближчі 3 дні» — про це чесно пише у `warnings`, але
  календарної логіки в агента немає.
- Провайдер періодично віддає `429`, і LangChain піднімає це як `ValueError` уже після відповіді.
  Тому прогін кейсів обгорнутий у три спроби з паузою — інакше одна помилка провайдера втрачала
  результати всіх наступних кейсів.

**Захисні механізми.** `max_steps=2` спрацював саме так, як задумано: агент устиг зібрати погоду
і факти для обох міст (6 викликів за 2 кроки), був зупинений і все одно дав корисне порівняння,
позначивши в `warnings`, чого не встиг. `timeout=5s` зупинив агента після першого кроку —
у відповіді немає погоди, і саме це написано у `warnings`.

**Детекція зациклення** у живих прогонах не спрацювала жодного разу: модель не повторювала
однакові виклики. Механізм відтворюється тестом
`tests/test_graph.py::test_repeated_tool_call_is_detected`, де фейкова модель двічі просить
`geocode({"city": "Львів"})` — другий виклик не виконується, агент іде у `respond`.

## Тестування

28 офлайн-тестів, жодного звернення до мережі чи до платного API:

- `tests/test_tools.py` — валідація (порожнє місто, `days=8`, `code="US"`, `amount=0`,
  посилання замість назви статті), нормалізація (`" usd "` → `USD`), розбір відповідей API
  та перетворення мережевої помилки на зрозуміле повідомлення.
- `tests/test_graph.py` — `max_steps`, `timeout` (перевіряється, що до LLM справа навіть не
  дійшла), детекція повторів, форма траєкторії, повторне використання скомпільованого графа.

Мокається межа: `requests.get` для інструментів і сам об'єкт LLM для графа. Тверджень про
конкретні формулювання моделі немає — лише про структуру.

## Інженерні рішення

**Чому траєкторія збирається з історії повідомлень, а не пишеться в стан покроково.**
`state["messages"]` уже містить усе: питання, tool calls, спостереження. Дублювати їх у
паралельний список означало б два джерела правди, які роз'їдуться. `trajectory_from()` —
чиста функція від історії, її легко тестувати.

**Чому детекція зациклення стоїть після виклику LLM, а не в роутері.** Роутер у LangGraph не
може писати в стан. Перевірка одразу після відповіді моделі дає ще одну перевагу: повторний
виклик інструменту навіть не виконується, тобто зайвого HTTP-запиту не буде.

**Чому помилки інструментів — це `{"error": ...}`, а не винятки.** Виняток убив би граф;
рядок з описом помилки повертається моделі як спостереження, і вона може виправити аргументи
або чесно сказати користувачу, що даних немає. Кейс `nonexistent_city` — саме про це.
